# neb-storage

Synchronous, read-only Local / WebDAV / S3 adapters for the command service. The first alpha supports browse, streaming download, system credential storage and safe local publication. Remote upload and bidirectional synchronization are intentionally unavailable; the UI must say so.

`StorageRegistry::open(data_dir)` loads sanitized source settings without network or credential-store access. `add(AddStorageRequest)` adds or reconnects a location; identical kind/endpoint/root/bucket preserves its ID. `remember_credentials` defaults to true for new requests. Remote credentials then live in Windows Credential Manager, macOS Keychain or Linux Secret Service, accessed through `keyring` with explicit platform backends. Linux D-Bus secret transfer uses the Rust cryptography backend; a running, unlocked desktop Secret Service is required. Unsupported or locked stores fail explicitly; there is no plaintext fallback. A private serialized payload goes only into the system store, never the config/database/API/logs. Credential structs are not `Debug`/`Serialize` and their strings and temporary vault buffers are cleared on drop.

Credential records are keyed by the canonical profile directory, source ID and source location; copying a configuration into another profile or changing its endpoint cannot silently send an existing secret to that location. Moving the profile requires reconnecting. Saves are read back and verified before the nonsecret config is published. If settings publication fails, the prior vault record is restored; rollback failure is reported. These operations are not a transaction across multiple concurrently running Nebulume processes. Setting `remember_credentials=false` removes any saved record before keeping credentials for this session; removal failure is reported, without claiming the record was deleted. Local sources never access the vault.

For an existing location, omitted/empty credential inputs retain available stored or session values. Changing a WebDAV username or S3 access key requires the corresponding new secret. An S3 token is retained when re-entering the same key pair, but is not carried to a different access key. A new S3 source requires a full access/secret pair; a new WebDAV source with no username is anonymous. Old configurations lacking `remember_credentials` remain session-only and need one reconnect to save their credentials securely. `credential_status` is `system`, `session`, `missing`, `unavailable`, or `not_required` (local). After reopening, `system` means a saved vault reference is configured; actual access is lazy and may subsequently change to `missing` or `unavailable`. Such failures never prevent startup.

`connected` is false after open/add and reflects the latest actual browse/read/check result, not the presence of credentials. `check(id)` browses the configured root and returns `{id,connected,credential_status,checked_at,error}`; network, authentication and vault errors produce `connected=false` plus a safe error, while an unknown source ID is a command error. `local_root(id,prefix)` returns a checked local directory for library integration. `browse(id,prefix,limit,cursor)` returns immediate children, up to 1,000 per page. S3 uses native ListObjectsV2 continuation tokens; WebDAV and local cursors are sorted last keys. WebDAV servers still return a full depth-one response and are bounded at 16 MiB.

For separate CLI invocations, credentials can also be supplied through source-specific environment variables at registry startup. The prefix is `NEBULUME_STORAGE_<UPPERCASE_ID_WITH_HYPHENS_REPLACED_BY_UNDERSCORES>_`. S3 reads `ACCESS_KEY`, `SECRET_KEY`, optional `SESSION_TOKEN`; WebDAV reads `USERNAME`, optional `PASSWORD`, or `ANONYMOUS=1` for public sources. Complete environment credentials override the saved record for that session, including while the vault is locked. Reading them does not persist them or mark the source connected. A subsequent explicit `add` with remembering enabled may save the credentials selected by that request. A long-running CLI stdio session can retain session-only credentials in memory.

`reader(id,key)` streams; `fetch(id,key,destination)` pins the selected parent directory, writes to a random sibling temporary file, flushes, verifies complete SHA-256 by reading the temporary file again, and atomically publishes by creating a hard link without replacement. It then verifies the published file too. Original remote objects are never altered. Transfers have a 15-second connection and 300-second request timeout in this alpha; large transfers that exceed that timeout fail and can be retried.

Storage keys reject absolute paths, traversal, Windows drive syntax, separators, reserved names and control characters. Existing symlinks/reparse points are rejected; local opens are additionally capability-relative. HTTP redirects and automatic proxies are disabled. WebDAV response paths must remain within the configured origin/root. S3 uses SigV4 path-style requests, explicit credentials and region (default `us-east-1`); ETags are not treated as SHA-256. S3 session tokens are supported by the library input.

HTTP is available for explicitly selected LAN endpoints: IPv4 RFC1918, loopback and link-local; IPv6 loopback, unique-local and link-local. IPv4-mapped IPv6 is classified by the embedded IPv4 address. Public, unspecified, multicast and other reserved ranges are rejected. Domain names must resolve entirely to allowed LAN addresses; mixed public/private answers are rejected. The validated address set is fixed in that source's client, preventing a second DNS lookup from changing its destination. Reconnect to refresh changed NAS addresses. IPv6 link-local URLs requiring a scope identifier are not currently supported by the URL parser; use a reachable ULA or LAN hostname instead.

HTTPS normally validates the public CA chain and hostname. For a LAN self-signed/private-CA server, `inspect_tls(endpoint)` makes a credential-free TLS handshake and returns `endpoint`, leaf-certificate `sha256`, `subject`, `issuer`, RFC3339 `not_before`/`not_after`, and `subject_alt_names`. It sends no HTTP request and does not save trust. Its socket operations share a 15-second deadline after system DNS resolution; OS resolver timing remains platform-dependent. Expired/not-yet-valid certificates and invalid handshake signatures are rejected even during inspection.

After an explicit user trust decision, `AddStorageRequest.tls_certificate_sha256` accepts the leaf DER SHA-256 as 64 hexadecimal digits (colon separators accepted). It is stored as lowercase hex and applies only to that source's independently configured client. Pin mode permits an untrusted CA or a hostname/IP mismatch, but still checks the leaf's validity period and cryptographically verifies TLS 1.2/1.3 handshake signatures. A different certificate fails before HTTP credentials are sent. Pin mode is limited to LAN HTTPS with the same fixed-address policy as LAN HTTP; it is never a global "accept invalid certificates" switch. Missing/null pin retains or restores standard CA/name validation, including when reconnecting an existing location. Inspection requires independent fingerprint verification when the network is not trusted; discovery itself does not establish server identity.

Loading saved configuration performs no DNS or network access, even when environment credentials are present. Reopened sources restore remembered credentials and create their client lazily on the first remote operation; unavailable hosts then report the actual connection error without preventing application startup. Source settings and pins survive restart. Existing configurations without the pin field retain standard HTTPS validation.

`PreparedDestination` retains an existing ancestor handle while the user reviews an import. `ScopedDestination` creates and opens each child directory with no symlink following and performs temporary creation, verification, hard-link publication and cleanup through fixed directory capabilities. Replacing a directory pathname during a copy cannot redirect publication to the replacement. Destinations must support hard links: FAT/exFAT destinations fail explicitly and safely, with no unsafe fallback. FAT/exFAT source cards can be read normally. Remote endpoint compatibility still needs real service CI or explicitly provisioned test services. Tests use temporary files and loopback HTTP/TLS fixtures with generated certificates, never live accounts. TLS regressions cover valid/mismatched pins, wrong hostnames, validity windows, deliberately wrong signing keys for TLS 1.2/1.3, source isolation, trust removal, legacy configuration, offline startup, DNS address pinning, IPv6, and blocked redirects.

Credential regressions inject an isolated `CredentialStore` mock through `open_with_credential_store`, covering lazy authenticated restart, session-only mode, blank reconnects, source/profile isolation, unavailable/missing/corrupt records, environment override, rollback and forgetting. They do not write the user's vault. The ignored Windows native test uses a random synthetic service/entry, reads it back, deletes it and verifies absence; run it explicitly with `cargo test -p neb-storage windows_native_vault_roundtrip_cleans_up_its_entry -- --ignored`.

Reference APIs: [keyring 3.6.3](https://docs.rs/keyring/3.6.3/keyring/), [reqwest 0.12](https://docs.rs/reqwest/0.12/reqwest/), [S3 Signature Version 4](https://docs.aws.amazon.com/AmazonS3/latest/API/sig-v4-authenticating-requests.html), [WebDAV RFC 4918](https://www.rfc-editor.org/rfc/rfc4918).
