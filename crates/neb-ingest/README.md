# neb-ingest

`IngestService::open(data_dir)` owns reviewed in-memory import plans and durable file-result journals. `plan(source,destination,layout,deduplicate)` recursively discovers common raster/RAW/video formats plus XMP sidecars in any selected folder or mounted card. It does not register the card, add marker files, or write destination folders. `execute(plan_id)` only accepts a plan made in the current process, preserves every source, and records each file outcome; `history()` reports abandoned running jobs as interrupted.

The `preserve` layout retains paths below the source. The `date` layout uses EXIF DateTimeOriginal's camera-calendar date and the original filename; missing/unreadable capture dates go into `unknown-date`, with an explicit `date_source`. EXIF parsing reads at most a 16 MiB prefix; metadata outside it remains unknown. No file modification date is relabeled as capture time. RAW/video timestamp extraction and paired RAW/JPEG timestamp propagation are follow-up work; XMP sidecars currently retain their filenames but are not grouped semantically.

Planning hashes source bytes with SHA-256 and records length/mtime. Duplicate matching reads actual destination bytes after a size filter, including renamed files and identical content within the same batch. Execution reopens and hashes the source, rechecks every planned duplicate, and independently checks same-path conflicts. Different content receives a deterministic hash suffix. With deduplication disabled, identical files are copied under a new conflict name as well; that explicit mode intentionally creates another copy on repeated execution. New files are streamed to owned temporary files, synced, fully re-read and verified, then published without replacing existing files. A changed source fails only its file and appears in the result. Source/destination nesting is prohibited; links, reparse points, hidden files and unsafe paths are skipped with warnings. Discovery is bounded to 64 levels and one million files.

After each completed file a JSON journal is atomically replaced. A restart intentionally requires a fresh plan: actual destination files are hashed again, making completed files idempotent even if the process stopped between publication and its journal update. This is file-level recovery, not byte-range resume. Old temporary files may remain after a process crash and are never blindly deleted. The reviewed plan pins the destination ancestor; per-file publication stays within fixed directory handles, including when a pathname is replaced during copying. Atomic no-replace publication requires hard-link support: FAT/exFAT destinations return a visible error, while FAT/exFAT source cards work normally. This alpha runs serially; cancellation, removable-volume event detection, copy concurrency, remote destinations and job resumption UI are later milestones.

## Reference project assessment

Read-only review of the reference project `photo-import-assistant` followed its AGENTS.md. Useful design sources are `src/TransferEngine.cs` (SHA-256, temporary ownership, no-replace publication), `CandidatePlanner.cs` (read-only planning and source/target path separation), `RemoteTransferEngine.cs` (streaming upload/readback), `ImportScheduler.cs` (bounded work scheduling), and `docs/architecture.md` / `organization.md` (frozen plans, honest date provenance, deletion constraints).

Its latest configuration has no personal server/credential defaults, but product boundaries remain Windows/.NET 4.8, removable disks only, DCIM-only discovery, writable card UUID markers, a Nikon-centered RAW list, and SMB-specific deletion authorization. Nebulume generalizes the source to a selected mounted folder, supports more format extensions, does not alter the card, and never offers source deletion. The reference explicitly does not provide cross-restart byte resume; Nebulume's durable journals and verified replanning establish file-level recovery first.

Acceptance tests cover: same size/different bytes, renamed duplicates, destination changes after planning, source changes after planning, filename conflict protection, read-only plans, unknown capture dates, source retention, restart idempotency, invalid/absent plan IDs, and link rejection. These are meaningful safety assertions; they use synthetic bytes in temporary directories, not personal media or actual cards.
