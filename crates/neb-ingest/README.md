# neb-ingest

`IngestService::open(data_dir)` owns reviewed in-memory import plans and durable file-result journals. `plan(source,destination,layout,deduplicate)` recursively discovers common raster/RAW/video formats plus XMP sidecars in any selected folder or mounted card. It does not register the card, add marker files, or write destination folders. `execute(plan_id)` only accepts a plan made in the current process, preserves every source, and records each file outcome; `history()` reports abandoned running jobs as interrupted.

The `preserve` layout retains paths below the source. The `date` layout uses EXIF DateTimeOriginal's camera-calendar date and the original filename. Images and XMP sidecars are paired only by the exact same source-relative directory and filename stem. An image's own EXIF date is marked `exif`; companions without EXIF inherit a single unambiguous group date and are marked `paired_exif`. Multiple distinct group dates produce an explicit warning: images keep their own dates and undated companions remain in `unknown-date` with `date_source=unknown`. A different folder or stem never supplies a date. EXIF parsing reads at most a 16 MiB prefix; metadata outside it remains unknown. No file modification date is relabeled as capture time. Additional RAW/video timestamp extraction remains follow-up work.

Planning hashes source bytes with SHA-256 and records length/mtime. Duplicate matching reads actual destination bytes after a size filter, including renamed files and identical content within the same batch. Different image formats remain separate (RAW and JPEG are never folded together). XMP groups preserve companion filenames: identical bytes are reused only at the same target path, so identical edit sidecars or photographs with different companion names are retained. If discovery or reading a known group member fails, the entire group is excluded from the reviewed plan with a warning; its remaining sidecars cannot be imported alone.

Before the first member of an XMP group is published, every planned target in that group is checked through the fixed destination handle. Any occupied name that cannot be safely reused blocks the entire group, including when deduplication is disabled. Different source groups that converge on the same destination stem are blocked before publishing any member of the affected XMP groups. Stem reservations are conservatively case-insensitive for portable destinations. Individual companion files are never renamed independently: choose a new destination directory or preserve the source folders instead. If a member fails during execution, no later member of that group is published. Previously verified files remain and the job reports a partial result. This is preflight plus failure containment, not a group-wide atomic transaction: there is no rollback or lock against external edits, and concurrent destination changes after preflight may still leave an incomplete or externally changed group. Retry the complete group in a new directory after resolving the failure.

Execution reopens and hashes the source and rechecks every planned duplicate. For photographs without sidecars, different content receives a deterministic hash suffix; with deduplication disabled, identical files receive a new conflict name as well. New files are streamed to owned temporary files, synced, fully re-read and verified, then published without replacing existing files. A changed standalone source fails its file; a changed companion source stops its remaining group. Source/destination nesting is prohibited; links, reparse points, hidden files and unsafe paths are skipped with warnings. Discovery is bounded to 64 levels and one million files.

After each completed file a JSON journal is atomically replaced. A restart intentionally requires a fresh plan: actual destination files are hashed again, making completed files idempotent even if the process stopped between publication and its journal update. This is file-level recovery, not byte-range resume. Old temporary files may remain after a process crash and are never blindly deleted. The reviewed plan pins the destination ancestor; per-file publication stays within fixed directory handles, including when a pathname is replaced during copying. Atomic no-replace publication requires hard-link support: FAT/exFAT destinations return a visible error, while FAT/exFAT source cards work normally. This alpha runs serially; cancellation, removable-volume event detection, copy concurrency, remote destinations and job resumption UI are later milestones.

## Reference project assessment

Read-only review of the reference project `photo-import-assistant` followed its AGENTS.md. Useful design sources are `src/TransferEngine.cs` (SHA-256, temporary ownership, no-replace publication), `CandidatePlanner.cs` (read-only planning and source/target path separation), `RemoteTransferEngine.cs` (streaming upload/readback), `ImportScheduler.cs` (bounded work scheduling), and `docs/architecture.md` / `organization.md` (frozen plans, honest date provenance, deletion constraints).

Its latest configuration has no personal server/credential defaults, but product boundaries remain Windows/.NET 4.8, removable disks only, DCIM-only discovery, writable card UUID markers, a Nikon-centered RAW list, and SMB-specific deletion authorization. Nebulume generalizes the source to a selected mounted folder, supports more format extensions, does not alter the card, and never offers source deletion. The reference explicitly does not provide cross-restart byte resume; Nebulume's durable journals and verified replanning establish file-level recovery first.

Acceptance tests cover: same size/different bytes, renamed duplicates, destination changes after planning, source changes after planning, filename conflict protection, read-only plans, capture-date pairing and ambiguity, source retention, restart idempotency, invalid/absent plan IDs, and link rejection. Group tests include a single occupied RAW, a single occupied XMP, cross-folder date-layout collisions, successful publication followed by a member failure, and a Windows share-locked source that excludes the complete group at planning. These are meaningful safety assertions; they use synthetic bytes in temporary directories, not personal media or actual cards.
